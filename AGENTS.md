# FairFold: agent operating rules

Read this file at the start of every session. It is the master prompt. Each session also gets one short
batch prompt from `prompts/`. Do that batch and nothing else.

## What this project is

FairFold is an AI-powered, explainable recruitment platform. Django 5.2 monolith, DRF with JWT
(simplejwt), Django templates + HTMX for the MVP UI (AD-002), Celery + Redis, PostgreSQL 17 + pgvector,
Docker Compose. AI screening is **advisory**: a human decides, every action is audited, and candidate
identity stays hidden from employers until shortlist.

## Where truth lives (in this order)

1. `FAIRFOLD_Project_Architecture_and_Requirements.md` (Arch Doc): requirements (§4.1), DDL (§5.1), ADRs, acceptance criteria (§10). **Canonical.**
2. `FAIRFOLD_Complete_Project_Document.md`: API list (§C.12), migration/seed strategy (§C.8), roadmap. **Canonical.**
3. `prd.md`: product requirements. It proposes; the Arch Doc decides.
4. `design.md`: UI specs, 78 page specs, wireframes, design tokens.
5. `HISTORY.md`: a log. It can be stale. **Verify its claims against the code before relying on them.**

The code in the repository beats any description of the code.

## Working method

- One batch per session. Never start the next batch. Never commit, push or open PRs. Leave the working tree for me to review.
- Do not expand scope. Something out of scope goes under "Observations" in your report; do not fix it.
- Do not invent requirements, columns, tables, endpoints or roles. Cite the requirement ID or doc section for every behaviour you implement.
- **Spec first.** If the code needs something the docs do not contain (a column, a table, an endpoint, a role), stop and propose the doc amendment. Amend the canonical docs, run `python scripts/verify_docs.py`, and only then write code. Counts such as 32 tables, 63 FRs, 51 FKs are asserted in several files and checked in CI; grep the whole repo for any number you change.
- If a prerequisite is missing, broken or contradicted by the docs, **stop and report**. Do not work around it.
- If you are unsure which of two documented behaviours is right, ask. Do not pick silently.
- Reuse existing code and dependencies. Do not add a library, an auth system, or a new pattern without asking first.
- Follow existing naming and style. Comments explain *why*, as in the existing code.

## Repo conventions that have already caused bugs

- Tests live in `tests/<app>/test_*.py`. Never in `<app>/tests.py` (those are empty placeholders and pytest does not collect them).
- Database tests run against PostgreSQL from Docker Compose. There is **no SQLite fallback and no `config/settings/test.py`**. The tests use `config.settings.ci`.
- Do not `source .env` before running pytest; `DEBUG=True` breaks `tests/core/test_production_settings.py`.
- Never put `__all__` in a settings module. It silently empties `INSTALLED_APPS` and `manage.py check` still passes.
- Migrations are generated (`makemigrations`), reviewed, and never edited after being applied. CI runs `makemigrations --check`. Hand-written migrations are only for data migrations.
- Roles are Django **groups** seeded from `core/fixtures/groups.json`, checked with `has_perm`. Do not add a `role` column. `has_role` is advisory only.
- Use `User.is_locked()`; never read `locked_until` directly.
- Anonymous endpoints must set `permission_classes` explicitly. The global default is `IsAuthenticated`.
- A green `docker compose ps` is not evidence the app works. Request the endpoint and read the response.
- Frontend assets (`tailwind.css`, `htmx.min.js`, `chart.min.js`) are generated by `npm run build`. A missing script is a silent no-op.
- Never fabricate research, statistics, test results, interview counts or benchmark numbers. "Not done" beats an invented result.

## Privacy and fairness invariants (never weaken these)

- PII is stripped before any AI call. Resume text is stored only after stripping; raw text is never persisted or logged.
- Employers see a per-employer alias, never name, photo, contact details or the internal UUID, until the candidate is shortlisted. Reveal is audited. (REQ-FR-029, 054)
- Ranking inputs never include paid tier, "Promoted" status or visibility. `rank_applications()` takes no such argument. (REQ-FR-053)
- A hard filter may only produce `not_matched`, never `rejected`. `not_matched` candidates stay reviewable with their reason and rule-set version. (G3)
- A shortlist/reject against the ranking needs a written reason, enforced in the database and the service. (REQ-FR-052)
- A required assessment blocks shortlisting in the **backend**, not only in the UI. (REQ-FR-051)
- Messages and interview-coaching data never enter any AI pipeline or `match_score`. (REQ-FR-043, 060)
- `AuditLogEntry` is append-only and must never hold PII or rationale text.
- Do not describe the product as "bias-free" anywhere. The wording is "explainable". `verify_docs.py` flags it.

substitute a different check and call it equivalent.

## Verification rules

1. Write tests with the code: success cases **and** failure and permission cases.
2. Run targeted tests first, then `manage.py check`, then the relevant regression tests and linters.
3. Report real output. Never say a test passed unless you ran it. Say exactly which commands you could not run.
4. Read `git diff` for unrelated changes, secrets, deleted files and debug output.
5. Separate failures that existed before your change from failures you caused. Fix only your own.
6. UI work: build to the page spec and wireframe in `design.md` §10, mobile (360px) first, with the design tokens in `static/css/tokens.css`. Use `--ai` violet only for AI-generated content.

## Progress tracking (every batch, before the final report)

Update these three files, with verified facts only:

1. `docs/PROGRESS.md`: change this batch's `- [ ]` line to `- [x]` and add the date and a one-line test result. If you are blocked, use `- [!]` and give the reason.
2. `docs/TRACEABILITY.md`: for each REQ-FR the batch covers, set the status to `done` only if every acceptance criterion is demonstrated by a passing test. Otherwise set `partial` and say what is missing.
3. `HISTORY.md`: append a dated entry at the very end of the file under `## 7. Batch log` (create that heading if it is missing). Include what changed, commands run with results, and known limitations.

Never edit older HISTORY entries except to correct a fact, and say that you did. Never mark anything done that you did not run.

## Final report format (always)

1. What changed
2. Files changed
3. Commands run and their actual results
4. Commands I could not run, and why
5. How I can verify manually (exact steps)
6. Known limitations and blockers
7. Observations (out of scope, noticed in passing)
8. Progress updates made (the three files above)
9. Suggested next batch

Then stop.
