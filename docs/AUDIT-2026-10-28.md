# Repository audit — 2026-10-28 (ponytail-audit)

Read-only quality audit of the working tree at commit `75dd6ed`. Nothing was changed.
Eight findings, numbered across the three groups so they can be referenced as "fix 1 and 5".

## What this repo does

FairFold is a Django 5.2 recruitment platform that tries to make screening explainable:
candidates register, get verified by email, build a profile and upload a PDF resume; employers
register, create a company profile and (in later batches) screen candidates. Uploads go
browser → object storage via presigned URLs with a ClamAV scan gate, and every risky action is
meant to leave an audit row.

**Load assumed:** one deployment — a single VPS behind nginx, `3` gunicorn workers and `2` celery
workers, a few hundred candidates and employers. Not a high-traffic multi-region service, so
micro-optimisations were ignored and anything that breaks or leaks *once deployed* was ranked
higher.

**How this was checked.** By reading code. `pytest`, `manage.py check`, migrations and HTTP
requests could not run in the audit environment (no virtualenv, no Django/pytest installed, no
Docker stack), so every "N passed" figure in the repo is unverified here. The one thing that was
run: `ai/bias_pass.py` directly with system Python — a text containing "Graduated in 2026",
"women's college" and "Age: 22 years old" flags four signals, and "BBA, Some College, 2023" flags
nothing.

## Must fix

### 1. In production, a candidate can never upload a resume — and with a bucket configured, the app fails to boot

**File:** `config/settings/production.py:183-185`

- **What this is:** `base.py` turns on S3 storage when `AWS_STORAGE_BUCKET_NAME` is set.
  `production.py` then unconditionally sets the default storage back to `FileSystemStorage`.
- **Problem:** `presign_resume_put()` → `s3_client()` reads `default_storage.connection`, which
  `FileSystemStorage` does not have, so it raises `StorageError` and
  `POST /api/v1/candidates/resumes/` answers `503` every time. With a bucket set,
  `manage.py ensure_storage` raises `CommandError` and stops the boot. Either way, production
  cannot accept a resume, and files would live in an ephemeral container directory that a
  redeploy wipes. `HISTORY.md:3290` deferred this to batches 1.18/1.19, which have since shipped,
  so it is no longer pending anything.
- **Fix:** delete those three lines so the bucket switch in `base.py` stays the only authority,
  then (optionally) raise in `production.py` when `AWS_STORAGE_BUCKET_NAME` is empty — the feature
  cannot work without it, so boot is the right place to say so.
- **If we skip it:** the first real employer deployment discovers the product's core feature is
  dead, and any resume uploaded to a filesystem-backed host disappears at the next deploy.

### 2. The pending page prints a working verification link for any address typed into the signup form

**File:** `accounts/views.py:195-234` (`check_email`)

- **What this is:** After signup, `/register/check-email/` renders the full verification URL for
  whatever address is in the session — no mailbox needed, not gated on `DEBUG`.
- **Problem:** Anyone can type a victim's address into the public signup form and gets a live
  token for that account, so a stranger can verify an address they do not own — and can register a
  real person's address first and complete it without ever seeing their inbox. The README and the
  view docstring both say this must be re-gated before the app is reachable by other people, so
  this is a known blocker rather than a surprise; it is listed because it is the single most
  exploitable thing in the tree today.
- **Fix:** restore the `EMAIL_VERIFICATION_LINK_IN_UI` setting that `HISTORY.md` describes
  (default `DEBUG`), and render the link only when it is on.
- **If we skip it:** the first public day lets anyone claim and verify an address that is not
  theirs.

## Should fix

### 3. An employer who signs in lands on the public landing page

**File:** `accounts/views.py:341-368`

- **What this is:** `role_landing_url()` maps employer roles to `reverse("employers:dashboard")`.
- **Problem:** No `dashboard` route exists in any namespace — the employer HTML namespace is
  `employer_portal` with `onboarding/`, `company/`, `company/edit/`. So `reverse` raises
  `NoReverseMatch`, the `except` swallows it, and every employer and interviewer is redirected to
  `/`. Nothing catches it because `tests/accounts/test_login_ui.py` only tests the candidate
  landing. The silent `except NoReverseMatch` is what turned a typo into a permanent wrong
  destination.
- **Fix:** point the three employer tuples at `"employer_portal:company"` (which forwards a
  profile-less employer to onboarding), delete the `try/except NoReverseMatch`, and add one test:
  employer credentials → `302` to `/employer/company/`.
- **If we skip it:** every employer thinks sign-in failed, because they arrive back on the
  marketing page.

### 4. The stored resume size is the browser's claim, not the file's size

**File:** `candidates/api_views.py:319, 355-359`

- **What this is:** The completion endpoint measures the object (`inspect_upload` returns the real
  size) but binds it to `_size` and saves only `status` / `status_reason`.
- **Problem:** A client that declares `file_size: 1000` and uploads a 5 MB PDF passes every check
  (the real size is under the limit, the sniffed type matches), and the row then reports `1000`
  forever through `ResumeSummarySerializer.file_size`. The one number the server actually measured
  is thrown away and replaced by an unverified one.
- **Fix:** `size, sniffed = inspect_upload(...)` and include `"file_size"` in the `update_fields`
  when moving to `scanning`; one extra field, no new logic.
- **If we skip it:** the resume API reports a size that has no relationship to the stored object,
  which is exactly the kind of number a support ticket will be about.

### 5. A presigned upload has no size limit, and an object whose client never "completes" is never deleted

**File:** `candidates/uploads.py:110-135`; `core/storage.py:apply_cors` (no lifecycle rule)

- **What this is:** The PUT URL signs only bucket, key and content type. The declared `file_size`
  gates whether a URL is issued — it is not part of the signature — and the size check runs in a
  separate completion call the client chooses to make.
- **Problem:** One candidate account can request a URL, PUT a multi-gigabyte object, and never call
  `complete/`. `discard_object` only runs on rejection or delete, and the bucket has no expiry
  rule, so the bytes stay. The completion check protects the product from *keeping* a bad file, not
  from *storing* it. (The missing rate limit is already recorded as outstanding; the unbounded
  object size and the never-collected orphan are not.)
- **Fix:** sign a POST policy with `content-length-range` instead of a presigned PUT (S3 and MinIO
  both enforce it, and the object store then refuses the oversize body), or add a lifecycle rule to
  `ensure_storage` that expires objects under `resumes/` after a day unless the row moved on.
- **If we skip it:** disk on a single-host deployment is fillable by one account, and the failure
  looks like "storage is mysteriously full".

## Nice to have

### 6. `CompactPagination` has no user

**File:** `core/pagination.py:48-56`

- **What this is:** A second paginator class for reference-data selects, with `page_size = 50` and
  a `max_page_size = 200` ceiling.
- **Problem:** Nothing in the repo references it — not a view, not a test, not a template. It was
  written for endpoints that do not exist yet, and the 200-row ceiling it carries is higher than
  the 100 the project enforces everywhere else.
- **Fix:** delete the class; the batch that needs it can add it against a real endpoint.
- **If we skip it:** someone will import it for the higher ceiling and quietly bypass the
  documented 100-row limit.

### 7. `LOGIN_REDIRECT_URL` points at a page that does not exist

**File:** `config/settings/base.py:359`

- **What this is:** `LOGIN_REDIRECT_URL = "/dashboard/"`, but no `/dashboard/` route exists.
- **Problem:** Nothing reads it today (the login view picks a destination itself), so it is dead
  config that reads as a working fallback. The moment someone adds
  `django.contrib.auth.views.LoginView` or a `RedirectView` that uses it, sign-in ends in a 404
  that looks like a routing mystery.
- **Fix:** delete the line, or set it to `"/"`.
- **If we skip it:** a future auth change inherits a broken default that no test covers.

### 8. Production's cache location can be `None`, against the file's own rule

**File:** `config/settings/production.py:192`

- **What this is:** The module states that every value is required and a missing one raises at
  boot, then sets `CACHES["default"]["LOCATION"] = env("REDIS_URL")`, which returns `None` when
  unset.
- **Problem:** With `REDIS_URL` missing, boot succeeds and the first cache use — the login lockout
  counter, the resend cooldown, the health probe — fails at request time instead of at deploy time.
  That inverts the promise the rest of the file keeps.
- **Fix:** `env_required("REDIS_URL")`, imported explicitly like the other names in that file.
- **If we skip it:** a missing variable turns into unexplained 500s on login rather than a deploy
  that refuses to start.

## Verdict

A healthy, unusually disciplined codebase — the auth, upload, scan and audit paths all have failure
tests — but fix **1** before any deploy (it breaks the product's core flow), **2** before the site
is reachable by anyone, and **3** because it is a silent `NoReverseMatch` that a single test would
have caught.

**Lean:** -6 lines, -0 dependencies possible. The six are `CompactPagination`; the unused heavy
dependencies in `requirements.txt` (torch, transformers, sentence-transformers, spacy) are for
Phase 2, so removing them now would just be re-adding them later.
